## Context

官方 Telegram 源码位于 `work/upstream-official/Werewolf for Telegram`，QQ 版位于 `werewolf-python`。当前核心规则已有较多实现和对照测试，但 Telegram 的按钮式分步操作、群级配置、辅助命令和提示内容仍未完全映射。实现必须保留现有 QQ Gateway、Docker、PostgreSQL 和已有数据。

## Goals / Non-Goals

**Goals:**

- 以官方源码和官方语言文件建立一份可追溯的规则、阶段、命令对照表。
- 把游戏状态、身份行动和 QQ 消息交互对齐到同一套规则结果。
- 让群配置持久化、隔离，并能在容器重启后正常使用。
- 用自动化对照测试覆盖身份、阶段、命令和失败分支。

**Non-Goals:**

- 不运行 Telegram 机器人，不改变官方源码。
- 不更换 QQ Gateway、数据库或 Docker 运行方式。
- 不做与官方玩法无关的界面重做、性能重构或新身份设计。

## Decisions

### 以官方源码建立行为清单

先读取官方角色、阶段、命令、设置和语言文件，形成逐项清单；每项清单绑定 QQ 中的行为和测试。这样可以避免只测主流程而漏掉特殊身份和错误分支。直接凭现有测试补功能的方式无法证明覆盖完整，因此不采用。

### 保留现有游戏核心，补齐缺口

优先复用 `werewolf-python` 已有的状态和规则代码，只在缺失处补逻辑、提示和状态字段。只有当现有状态无法表达官方多步骤行动时，才增加明确的行动会话状态。整体重写会增加数据迁移和回归风险，因此不采用。

### QQ 使用统一的文字指令加分步会话

QQ 不能直接照搬 Telegram 按钮，所以采用命令触发、机器人逐步询问、玩家回复目标、最后确认的方式；快捷指令和官方命令名保持一致。每一步都绑定玩家、群、房间、回合和有效期，避免串房间或重复执行。

### 群配置独立持久化

配置以群标识为主键保存，缺省值来自官方默认设置；开始一局时生成不可变的本局设置快照。这样修改下一局配置不会改变正在进行的游戏，也不会影响其他群。数据库迁移必须可重复执行并保留旧字段。

### 官方文本集中管理

角色名、阶段名、错误提示、死亡原因、结算文本和命令帮助集中维护，并保留官方消息所需的变量。测试同时检查关键文本和变量内容，避免规则已经正确但玩家不知道下一步怎么做。

## Risks / Trade-offs

- [官方源码和当前 QQ 行为存在隐含差异] -> 先完成逐文件清单，再把每项差异转成场景测试；未覆盖项不得宣称完成。
- [QQ 私聊或群聊消息丢失] -> 行动提交使用幂等标识，超时可恢复，重复消息只返回当前状态。
- [旧数据库没有群配置] -> 使用一次性迁移和官方默认值补齐，部署前备份数据库。
- [菜单注册受平台限制或失败] -> 消息指令仍可用，状态页记录菜单同步结果并允许再次同步。
- [官方按钮流程映射到文字后容易产生歧义] -> 每一步只接受当前允许的编号或明确命令，并返回当前剩余选项。

## Migration Plan

1. 备份现有数据库和当前 Docker 配置。
2. 增加群配置、行动会话和必要阶段状态的兼容迁移，默认使用官方默认值。
3. 部署代码并执行官方对照测试、命令检查和容器重启检查。
4. 先让新规则只用于新开的房间，确认无误后处理旧房间；旧房间继续使用可恢复的状态格式。
5. 回滚时停止新容器，恢复上一个镜像和数据库备份；不删除新增字段，避免旧版本启动失败。

## Open Questions

无。实现所需的关键选择已固定，剩余差异应通过官方源码核对后转成任务和测试，不留给实现阶段猜测。
