## 当前情况

官方核心玩法集中在 `Werewolf Node/Werewolf.cs`，角色与分配规则还依赖 `Shared/Roles.cs` 和 `Shared/GameBalancing.cs`。旧计划按“夜晚、投票、胜负”等大类检查，不能证明大类内部的每个条件分支都已覆盖。本次采用“先盘点，后对照，冻结差异，再集中修复”的方法。

## 要达成和不做的事

**要达成：**

- 获得一张能计算完成度的官方分支总表，任何玩法结论都能追到官方来源和实际测试。
- 在改动前找齐当前官方版本的全部确认差异，避免修一条后才发现同一流程里的另一条。
- 让 QQ 文字指令进入与 Python 规则引擎相同的流程，并验证入口错误提示不会把用户引到机器人收不到的普通文字。
- 让每次修复都能恢复到修改前状态，并能证明恢复有效。

**不做：**

- 不承诺复制 Telegram 的按钮样式、动图、语言包、成就或菜单排版。
- 不根据未调用的历史代码臆造新玩法。
- 不用真人 QQ 对局替代程序化规则检查。

## 做法

### 1. 先生成官方分支总表

从官方开局、夜晚、白天、结束和命令入口开始，沿每个实际调用继续记录 `if`、`switch`、角色判断、随机判断、人数判断、设置判断和异常结束分支。每条记录是一个“输入条件到游戏结果”的最小单位；同一角色在不同阶段、不同目标状态或不同设置下的结果必须分成多行。

总表固定字段为：编号、官方文件、行号范围、调用来源、触发条件、官方状态变化、官方消息或事件、Python 文件与函数、测试名称、固定输入、期望结果、实测结果、状态、差异编号、复查日期。总表另有四个数字：总行数、已通过数、差异数、未检查或未决数。

### 2. 用状态而非文字判断相同

每条对照至少比较阶段、轮次、角色、阵营、存活、死亡原因、访问者、保护、转换、恋人、投票、胜方和事件。文字只检查 QQ 指令是否可用及提示是否把用户引向正确指令；不以 Telegram 的排版或表情作为玩法相同的依据。

### 3. 固定会变化的输入

随机规则使用可控制的随机源、`0%`、`100%`、官方固定概率和多次固定序列。人数规则使用最小人数、刚好触发人数、刚好不触发人数和常规人数。涉及多个夜晚、连锁死亡、重启恢复的规则使用完整状态快照，不能只调用孤立小函数。

### 4. 差异冻结后集中修复

检查阶段只新增总表和测试，不改规则实现。只有总表不存在未检查或未决玩法分支时，才冻结差异清单。随后按共享规则、角色动作、阶段推进、保存恢复、QQ 入口的顺序集中修改；每次修改同时通过该差异测试和受影响的既有测试。若修复产生新差异，重新打开相关总表行，直到差异数归零。

### 5. 结论前的双重复查

第一轮由官方分支总表逐行确认；第二轮从 Python 的规则入口反查，确认没有 Python 自己增加的会改变结果的分支。两轮的条目数与状态必须一致。只要存在没有官方来源、没有测试、没有结果或没有回退验证的玩法改动，就不得给出 `100%` 结论。

## 关键决定

### 把“每一个实际判断”作为最小检查单位

按模块或角色名称打勾容易漏掉同一角色在死亡、转换、投票和恢复时的不同判断。使用最小判断单位虽然总表更长，但能直接显示遗漏位置，因此采用。

### 先完整找差异，再统一改

边查边改会让后面的测试结果混入前面修复的影响，也会反复遗漏同一流程里的相邻判断。先冻结差异清单，再集中修复，能让“这次已找全”有可检查的边界。

### 100% 是结论，不是目标口号

只有总表、测试、实际运行结果和回退记录全部闭合，才写 `100%`。任何空白、跳过、未决或失败都会使结论保持未完成。

## 风险和处理

- [官方有历史代码但没有实际调用]：记录官方实际调用路径，避免 Python 擅自实现未调用行为。
- [随机结果造成偶然通过]：使用可重复输入和边界输入，必要时覆盖全部固定序列。
- [一处修复影响其他角色]：完成每个修复组后重跑相关组，最后跑完整检查。
- [QQ 平台显示不同]：把显示差异与文字指令的可用性分开记录，前者不影响玩法结论，后者必须通过。
- [修复后需要撤回]：每个修复组都保存原始文件哈希、副本、差异文件、验证记录和已验证的回滚脚本。

## 上线与回退

只在全部总表行通过后才更新本地 Docker 镜像。每个修复组先在副本上验证回滚脚本：回滚后对应差异测试恢复到修改前结果，再重新应用修改并确认测试通过。交付目录必须保留修改后文件、差异文件、验证记录和回滚脚本。
