## Purpose

让官方 Telegram 固定版本中每一条实际会改变狼人杀对局结果的规则判断，都能被逐条定位、稳定验证和复查，作为代码级复刻结论的唯一依据。

## ADDED Requirements

### Requirement: 官方实际玩法分支必须完整登记

系统必须从固定官方 commit 的实际游戏入口开始，登记每一个会影响身份、目标合法性、阶段、行动结果、死亡、转换、投票、胜负、保存恢复或命令结果的分支。每行必须有官方文件、行号、调用来源、触发条件、官方结果、Python 对应位置、测试名称、固定输入、实际结果和状态。官方未实际调用的历史代码必须单列并附调用证据，不能算入玩法总数。

#### Scenario: 登记官方角色判断

- **WHEN** 官方代码按角色、阵营、存活、目标、人数、概率或设置作出会改变对局结果的判断
- **THEN** 分支总表必须新增独立条目，不能仅以角色或模块名称代替该判断

#### Scenario: 遇到未调用历史代码

- **WHEN** 官方文件存在规则样式代码但从实际游戏入口没有调用路径
- **THEN** 总表必须标记为未调用并保留调用路径证据，Python 不得为它增加玩法

### Requirement: 官方玩法覆盖范围必须没有跳项

系统必须分别覆盖角色定义和分配、开局与房间状态、每个夜晚动作、每个白天动作、访问和阻止、保护和反噬、死亡链、转换和继承、恋人和墓穴、投票和超时、全部胜负判断、群设置、开局快照、重启恢复以及 QQ 文字指令入口。每个官方角色值及其在不同阶段触发的判断都必须单独完成对照。

#### Scenario: 检查一个角色的多个时点

- **WHEN** 同一角色在开局、行动、被杀、被投票、转换、恢复或结算中有不同官方判断
- **THEN** 每个判断必须各有一条总表记录和可重复测试，不得合并为一条“该角色已检查”

#### Scenario: 检查阶段推进

- **WHEN** 官方在等待、夜晚、白天、投票、结算或结束阶段改变流程
- **THEN** 总表必须记录进入条件、拒绝条件、超时条件、状态变化和后续阶段

### Requirement: 对照必须验证可观察的游戏结果

系统必须以阶段、轮次、角色、阵营、存活、死亡原因、访问、保护、转换、恋人、投票、胜方和事件等游戏结果作为对照依据。文字消息只用于验证 QQ 指令入口和用户提示；Telegram 按钮、动图、语言包、成就和菜单排版不得作为玩法一致性的判断依据。

#### Scenario: 官方和 Python 结果比较

- **WHEN** 使用同一固定初始状态和动作执行官方分支与 Python 分支
- **THEN** 测试必须断言相关游戏结果一致，并把输入和实际结果写回总表

#### Scenario: QQ 平台展示不同

- **WHEN** QQ 无法使用 Telegram 的按钮或排版形式
- **THEN** 总表必须记录为展示差异，并继续验证对应文字指令是否进入相同游戏流程

### Requirement: 会变化的规则必须使用稳定边界输入

系统必须为随机、概率、人数、超时、多夜晚和恢复规则提供可重复的输入。概率至少覆盖 `0%`、`100%`、官方固定概率和固定随机序列；人数至少覆盖最小人数、刚好触发人数、刚好不触发人数和常规人数。

#### Scenario: 概率规则检查

- **WHEN** 官方规则依赖随机数或概率
- **THEN** 测试必须在固定随机输入下重复得到同一结果，并覆盖成功与失败边界

#### Scenario: 人数规则检查

- **WHEN** 官方规则依赖玩家、狼人、恋人、墓穴或其他计数
- **THEN** 测试必须覆盖触发前、触发点和触发后的结果

### Requirement: 100% 结论必须有明确关单条件

系统只有在总表的未检查数、未决数和失败数均为零，全部差异已修复并复查，且反向检查未发现 Python 自行增加的玩法分支时，才可以标记代码级 `100%`。任一条件不满足时，结论必须为未完成并列出剩余条目。

#### Scenario: 存在空白证据

- **WHEN** 任一官方玩法分支缺少来源、Python 对应处、测试、实际结果或复查结果
- **THEN** 代码级 `100%` 状态必须保持未完成，并把该条目列为剩余工作

#### Scenario: 全部闭合

- **WHEN** 总表全部条目通过且反向检查没有额外玩法分支
- **THEN** 系统可以生成含总数、通过数、差异数、测试命令和退出状态的 `100%` 结论
